CONTEST-GAME · SYSTEM OVERVIEW

“这是谐音梗”系统设计与实现总览

面向玩家、创作者、管理员和联机房间的一体化谐音梗答题平台。本文档基于当前仓库源码、运行配置和已执行验证整理。

当前主线：M0 → M5 后端：Go + Gin + GORM 前端：Vue 3 + Vite + Pinia 运行依赖：PostgreSQL · Redis · MinIO
实现总结 里程碑 系统架构 目录介绍 优秀设计 整体流程 验证与剩余项

二、功能分层与用户能力

系统围绕四类角色展开：游客、登录玩家、创作者和管理员。

游客

浏览题集、游玩题目、查看提示与解释；答题进度写入 localStorage，登录后可以迁移到账户。

登录玩家

拥有 JWT 身份、跨设备进度、成就、投稿、媒体上传、我的投稿和联机房间能力。

创作者

通过投稿表单上传题面/媒体，查看投稿状态，等待管理员审核后进入公共内容流。

管理员

登录后台，审核投稿、批量通过/拒绝、管理题库、查看归档题目并恢复。

三、系统架构

新实现的后端接口遵循 handler → service → model 三层边界；main 是组合根，负责依赖装配和降级路由。

接口层与协议数据与缓存对象存储与实体客户端 / 边缘入口
边界原则Handler 不写业务规则，Service 不直接依赖 Gin/GORM/Redis，Model 负责外部存储细节；Service 通过窄接口依赖 Model，便于替换实现和进行单元验证。

backend/internal/handler 入口层
负责 JSON/form 绑定、JWT 上下文提取、WebSocket 升级、HTTP 状态码和统一响应。新模块如房间、媒体、限流、就绪检查都采用显式 Handler 结构体和构造函数。
backend/internal/service 逻辑层
负责输入校验、状态机、权限、事务编排和错误语义。例如 RoomService 只依赖窄化后的 RoomRepository，不感知 Redis 客户端细节。
backend/internal/model 数据层
负责 GORM 查询、Redis key/TTL/WATCH、MinIO 读写，以及迁移实体与数据库映射。它不把 Gin Context 传入上层。
backend/internal/entity 数据契约
集中定义 Player、Progress、MediaAsset、Room、PuzzleArchive 等跨层实体和房间事件模型，避免各层重复定义持久化结构。

五、实现中比较不错的设计

下面这些设计在当前项目里已经形成了可复用的工程模式，而不只是单点功能。

01

三层边界清晰

Handler → Service → Model 方向稳定。Handler 只负责协议，Service 负责规则，Model 负责存储。通过接口注入，Redis、GORM 和 MinIO 的实现不会扩散到业务层。

02

Redis 房间状态有并发保护

房间用 JSON + TTL 存 Redis，更新使用 WATCH + 事务 + 3 次重试。这比把玩家状态散落到多个 key 更容易恢复和广播，也降低了并发覆盖风险。

03

WebSocket 生命周期完整

每个连接有写锁、读限制、读写 deadline、ping/pong、旧连接替换和断开广播；重连时不会误删新连接的 presence，是 M4 中比较关键的稳定性处理。

04

依赖故障可见且可降级

/api/v1/ready 分别检查 PG、Redis、MinIO；缺少模块时路由返回明确的 503，避免依赖不完整时静默变成 404。

05

限流使用 Redis 原子脚本

固定窗口通过 Lua 将 INCR + PEXPIRE 放在一个原子操作里，主体先做 SHA-256 摘要，兼顾并发正确性、key 长度和敏感标识保护。

06

游客进度迁移保持渐进式

先读取服务端进度，再只上传本地缺失项；成功后清理本地 key。游客无需注册也能玩，登录后不会丢失已有进度，符合低门槛产品路径。

07

媒体访问走后端代理

MinIO 不直接暴露给浏览器，上传和下载经过后端 Handler/Service/Model，便于做用户归属、bucket 控制和后续鉴权策略。

08

生产部署与开发环境隔离

新增 docker-compose.prod.yml 和 edge，不改开发 Compose；生产只暴露 edge 端口，数据库和对象存储留在内部网络并使用持久卷。

09

验证证据覆盖真实依赖

不仅跑 Go/前端构建，还启动真实 PG、Redis、MinIO，验证双客户端房间事件、重连、就绪探针、限流 429 和 Nginx 代理路径。

六、系统整体流程图

下面的流程把公共答题、玩家账号、媒体投稿和联机房间放到同一条系统主链路中。

公共答题链路

玩家选择题集 → 获取题目 → 提交答案/提示 → GameService 判定 → 返回结果 → 登录玩家写入进度。

创作链路

登录 → 获取上传凭证/媒体代理 → 创建投稿 → 管理员审核 → 入库或拒绝 → 工坊浏览与试玩。

联机链路

JWT 建立 WebSocket → Redis 读取房间 → Ready/Start/Answer 事件 → Service 更新状态 → Handler 广播 → 全员结算。
